Project Summary

End-to-End QA Automation for automationexercise.com

A production-grade test automation framework built with Playwright and TypeScript, covering the full user journey on the live e-commerce site automationexercise.com — from registration and login through checkout, cart management, product search, accessibility auditing, visual regression, and network mocking.

All 11 test cases run on Chromium, Firefox, and WebKit browsers using a shared Page Object Model, custom fixtures, and a GitHub Actions CI/CD pipeline.

Notes for Live Site Testing

The test target automationexercise.com is a live site running behind Cloudflare. It can be intermittently slow. The framework handles this with:

  • Navigation timeout: 180 seconds per page load
  • Each test timeout: 300 seconds (600s for registration/checkout)
  • Automatic retry: 1 retry on failure (2 in CI)
  • Cloudflare 524 detection and page-reload recovery
  • Force-click to bypass ad-overlay interception

If tests fail due to site outages, wait a few minutes and re-run. Tests are designed to be retried safely.

Design Pattern

Test Specs (TC01–TC11)

11 test files in tests/. Each imports page objects and custom fixtures — no direct Playwright API calls; all interactions go through page objects.

Custom Fixtures

fixtures/pageFixture.ts extends Playwright's built-in fixtures using base.extend<T>(). Instantiates all page objects (loginPage, homePage, productsPage, cartPage, …) per test, injecting the shared page.

Page Object Model (POM)

7 page classes in pages/. All extend BasePage which provides navigate(), clickAndWaitForNav(), and Cloudflare recovery logic. No test assertions live inside page objects.

Utilities

utils/randomDataGenerator.ts — generates unique emails, names and passwords for each test run. utils/authHelper.ts — shared registerNewUser() and deleteAccount() helpers used by multiple test suites.

Test Data

testdata/products.json — static test data (payment card details, product info). Keeps data separate from test logic.

Key Technical Decisions

force:true on all navigation clicks

automationexercise.com injects Cloudflare <ins> ad elements that intercept clicks. All clickAndWaitForNav() calls use force:true to dispatch the click event directly on the target element, bypassing overlay detection.

Listing-page approach for "Add to Cart"

Instead of navigating to the product detail page to click the cart button (risking a 2nd Cloudflare timeout), we click .productinfo .add-to-cart directly from the products listing. Saves one navigation and reduces flakiness.

Cloudflare 524 detection & recovery

524 errors are served as valid HTTP (no exception thrown). BasePage.navigate() checks for h1:has-text("timeout occurred") with a 500ms timeout immediately after every navigation and retries if found.

Race-condition-free navigation

clickAndWaitForNav() starts the waitForURL listener before firing the click (in a Promise.all), so fast navigations that complete before a sequential listener registers are never missed.

GitHub Actions Workflow

The workflow file is at .github/workflows/playwright.yml. It runs automatically on push/pull-request to main or master, and can also be triggered manually from the Actions tab.

Trigger via GitHub UI

Go to your repository on GitHub

Navigate to the Actions tab at the top of the repo page.

Select "Playwright QA Capstone Tests"

Click the workflow name in the left sidebar.

Click "Run workflow"

Choose the browser (chromium, firefox, webkit, or all) from the dropdown and click the green button.

Download the HTML report

After the run completes, scroll to the bottom of the workflow run page and download "playwright-html-report" from the Artifacts section.

What the workflow does

# 1. Checkout code on ubuntu-latest # 2. Setup Node.js LTS + npm cache # 3. npm ci (install exact versions) # 4. Install Chromium browser with OS deps # 5. Run all tests EXCEPT visual (retries=2 in CI) npx playwright test --project=chromium --grep-invert "Visual Regression" # 6. Update visual snapshots for Linux CI environment npx playwright test tests/visual --project=chromium --update-snapshots # 7. Upload HTML report (30 days) + JUnit XML + traces on failure

Visual regression runs with --update-snapshots in CI because baseline snapshots are OS-specific (Linux CI vs Windows local). The CI always regenerates the baseline, so visual tests never fail in CI due to environment differences.

Presentation Q & A Preparation

Tap each question to see a model answer.

Why did you choose Playwright over Selenium or Cypress? ▼
Playwright was chosen for three reasons: (1) it supports all three major browsers — Chromium, Firefox, and WebKit — with a single API and a single install, which Cypress doesn't offer natively; (2) it has first-class TypeScript support and auto-waits built in, reducing the need for explicit waits; (3) page.route() for network mocking and toHaveScreenshot() for visual regression are built-in, whereas Selenium requires additional libraries for both.
What is the Page Object Model and why did you use it? ▼
The Page Object Model (POM) is a design pattern where each page of the application is represented as a class. The class encapsulates all selectors and actions for that page. Tests call methods on page objects instead of writing raw Playwright API calls. This means: (1) if a selector changes, you fix it in one place; (2) tests read like business scenarios ("loginPage.login(email, password)") rather than implementation details; (3) code reuse — the same registerNewUser() helper is shared across TC01, TC02-03 beforeAll, and TC07.
What are Playwright fixtures and how did you use them? ▼
Playwright fixtures are dependency-injection containers. The built-in page fixture provides a browser page per test. We extended this with base.extend<T>() in fixtures/pageFixture.ts to add all our page objects (loginPage, homePage, productsPage, etc.) as additional fixtures. Every test that uses { loginPage, cartPage } in its parameter list automatically gets fresh, fully initialized page objects without any setup boilerplate in the test itself.
How does the accessibility test work? ▼
TC09 uses the @axe-core/playwright library to run an automated WCAG 2.1 AA accessibility audit. After navigating to the home page, it calls new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze(). The result includes a list of violations categorized by severity (critical, serious, moderate, minor). The test asserts that there are zero critical violations. Serious and moderate violations are logged to the console for visibility but do not fail the test — this matches real-world QA practice where some existing site issues are acknowledged but don't block CI.
How does visual regression testing work? ▼
TC10 uses Playwright's built-in expect(page).toHaveScreenshot('home-page.png'). On the first run you pass --update-snapshots to create the baseline image, which is stored in a *.spec.ts-snapshots/ folder and committed to the repository. On subsequent runs, Playwright captures a new screenshot and compares it pixel-by-pixel against the baseline. If they differ beyond a threshold, the test fails and saves a diff image. Snapshots are stored per-OS and per-browser (e.g., home-page-chromium-win32.png) because rendering differs between platforms.
How does network mocking work in TC11? ▼
TC11 uses page.route() to intercept HTTP requests matching a URL pattern. Before navigating to the products page, we register a route handler that matches the products API endpoint. When the browser makes that request, Playwright intercepts it and fulfills it with a custom JSON response containing a mock product name (e.g., "Mock Test Product"). We then verify that the mock name appears in the rendered page. This tests that the frontend correctly renders API data without depending on the live API, making the test fast and deterministic.
How did you handle test data management? ▼
Two strategies were used: (1) Dynamic data — for user accounts, each test run generates a unique email address using RandomData.email() (timestamp + random suffix). This prevents test pollution between runs and allows parallel execution without conflicts. (2) Static data — payment card details and product info are stored in testdata/products.json and imported into tests. Account cleanup is handled in afterAll hooks using a deleteAccount() helper, so test accounts don't accumulate on the live site.
How did you handle flakiness on a live site? ▼
The site automationexercise.com runs behind Cloudflare and can return HTTP 524 timeout errors as valid HTML pages. We built several resilience layers:
  • 524 detection: After every navigation, check for h1:has-text("timeout occurred") with a 500ms timeout and retry if found.
  • Force-click: Cloudflare injects <ins> ad elements that intercept clicks. All navigation clicks use force:true to dispatch directly on the target element.
  • Long timeouts: Navigation 180s, test body 300s, heavy tests (registration, checkout) 600s.
  • 1 retry (2 in CI): Transient site outages recover on the retry attempt.
  • Try/catch in afterAll: Account cleanup failures don't propagate as test failures.
What does the CI/CD pipeline do? ▼
The GitHub Actions workflow (.github/workflows/playwright.yml) runs on every push and pull request to main. It: (1) checks out the code and installs Node.js LTS; (2) runs npm ci for a clean, reproducible install; (3) installs Playwright browser binaries with OS dependencies; (4) runs all 11 tests except visual regression (which uses --update-snapshots on Linux to handle OS-specific rendering differences); (5) uploads the HTML report as a downloadable artifact (retained 30 days), a JUnit XML report for integration with test dashboards, and traces for any failures. The workflow also supports manual dispatch with a browser selection dropdown.
What would you improve if you had more time? ▼
Several improvements could make this more production-grade:
  • Parallel workers: Currently workers=1 to avoid rate-limiting. A mock server or dedicated test environment would allow full parallelism and cut run time by 70%.
  • API-based setup: Use automationexercise.com's REST API to create/delete test users instead of navigating through the UI in beforeAll, making auth tests faster and more reliable.
  • Allure reporter: More visual test reports with trend history, screenshots, and step-by-step breakdowns.
  • Negative test cases: TC01–TC03 only test the happy path. Add tests for invalid credentials, duplicate registration, empty cart checkout, etc.
  • Environment config: Externalize the base URL and credentials as environment variables for multi-environment support (staging, production).
